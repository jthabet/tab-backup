# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tab Backup is a Firefox (Manifest V3) extension that backs up the current window's tabs to a file (JSON, Markdown, plain text or HTML bookmarks) and/or a synced bookmark folder, and reopens tabs from either. Published on Firefox Add-ons and the Chrome Web Store (ID `gapfigidccddefbabbcfcnapckpcdeap`), built from the same sources. Plain DOM JavaScript (no UI framework) + Tailwind CSS v4, bundled with webpack/Babel. Package manager is **pnpm**.

## Commands

```sh
pnpm install
pnpm build            # production build into dist/
pnpm start            # webpack watch, rebuilds dist/ (no Firefox launch)
pnpm dev              # watch + launch Firefox Developer Edition with a temp profile via web-ext-plugin
pnpm test             # builds dist/ and dist-chrome/, then unit + page tests (node --test test/), no browser needed
pnpm lint             # check-locales + test (which builds), then web-ext lint on dist/ (not ESLint)
pnpm build-extension  # package dist/ into web-ext-artifacts/ (run after pnpm build)
pnpm exec web-ext run # run an existing dist/ build in Developer Edition (webExt config in package.json)
make                  # clean + build + package
pnpm build:chrome     # Chromium build into dist-chrome/ (also start:chrome, dev:chrome, build-extension:chrome)
```

`pnpm test` runs dependency-free unit tests with Node's test runner: `test/fake-browser.js` stands in for the `browser` API (i18n from the real message files, in-memory storage, and Firefox- or Chromium-shaped bookmark trees), so `formats.js`, `backup-parse.js`, `i18n.js` and `bookmark-backups.js` run outside the browser. Read `process.env.BROWSER` where it's used, not in module-level constants, so tests can switch browsers with `installBrowser({ target })` (DefinePlugin still turns it into a constant in the build). `i18n.js` reads its language once at load, as the browser does, so its tests import it with a query string (`?ru`) to get a fresh copy per language. Page tests (`test/pages.test.js`, helpers in `test/page.js`) load the built `dist/` and `dist-chrome/` pages (HTML + bundled JS) into a happy-dom `Window` with the fake as `browser`, then click, type and pick files; they cover the popup, restore (every `samples/` format, HTML via happy-dom's `DOMParser`) and settings for both builds, and run against the build, so `pnpm test` builds first. Objects pages pass to the fake come from happy-dom's realm, so the fake stores Node-realm copies (e.g. `tabs.created`) for `deepStrictEqual`. Still keep logic that needs unit tests in a separate module (as `backup-parse.js` is for restore). Sample backups of three tabs in every format live in `samples/`. Also verify changes in the browser by loading `dist/manifest.json` via `about:debugging` → This Firefox → Load Temporary Add-on (Reload after each rebuild), and running the smoke test in `docs/DEVELOPMENT.md`. Use **Inspect** on `about:debugging` for runtime errors.

The `webExt` key in `package.json` must keep `sourceDir: "dist"`; `src/` imports CSS that only webpack can resolve, so web-ext cannot lint or load it.

## Architecture

- `src/` holds sources; Firefox must load the compiled `dist/`, never `src/` directly. Static markup (buttons, inline SVG icons, form controls) lives in the HTML pages; the JS only wires events and builds dynamic content with `createElement` + `textContent` (never `innerHTML`, which the AMO linter flags). Tailwind scans the HTML and JS for class names. webpack (`webpack.config.mjs`, context `src/`, `output.clean`) builds four entries — `background.js`, `popup.js`, `restore.js`, `settings.js` — and copies `manifest.json`, `popup.html`, `restore.html`, `settings.html`, and `icons/` verbatim into `dist/`. Any new page must be added to both `entry` and the CopyWebpackPlugin patterns.
- **background.js**: keeps the toolbar badge set to the total tab count, listening on `tabs.onCreated`/`onRemoved`. Each update lists every tab, so a burst of changes (restoring a backup, session restore at startup) is coalesced into one update 100 ms after the last change; tabs reported by `onRemoved` since the last update are left out of the count (Firefox bug 1396758: `onRemoved` fires before the tab is gone). The badge color is set once, on install and startup. Tested in `test/background.test.js` with `mock.timers`.
- **popup.js**: lists current-window tabs (click to activate). **Back up** serializes them with the format and file name pattern from settings and saves via `browser.downloads`; **Restore…** opens `restore.html` in a tab; the gear button opens the settings page.
- **restore.js** (+ **backup-parse.js**, which reads backups and maps URLs to `tabs.create` properties): the import flow, plus the list of bookmark backups (refreshed on `bookmarks.on*` events, keeping focus on the same button; not while a name is being edited), each with Restore, Rename (inline field: Enter or blur saves, Escape cancels) and Delete. Every restore (file or bookmark backup) first shows a preview with a checkbox per tab; tabs already open in any window start unchecked and unopenable URLs are listed but not selectable. Reads JSON backups fully and extracts http(s) links from Markdown, plain-text and HTML-bookmark backups, then calls `browser.tabs.create` per URL (mapping `about:newtab`/Reader View, skipping privileged URLs). Keep import UI on its own page rather than the popup, since the popup closes when the file picker opens.
- **bookmark-backups.js**: optional bookmark destination. Each backup is a dated folder inside a root folder (default name "Tab Backup", customizable in settings; created in Other Bookmarks, renamed with the translated `backupFolderTaken` message (e.g. "Tab Backup (backups)") if the user already has a folder of that name, in which case that name is saved back to the setting). The settings page shows the root's actual name (`getBackupFolderName`), so renaming the folder in the bookmarks manager is reflected there. The root is identified only by a marker bookmark inside it (`markerUrl()` + `MARKER_TITLE`, found via `bookmarks.search`; the Chromium build uses a GitHub marker URL, since the two browsers' bookmarks never sync), never by name, so user folders with the same name are never listed or pruned, and renamed/moved/synced roots are still found. Backups are pruned to the newest `keepBookmarkBackups`; before a save that would prune, the popup shows an inline confirmation listing the backups to be deleted (`backupsDeletedByNextSave`), since toolbar popups can't use `confirm()`. Changing `MARKER_TITLE` after release would orphan existing roots. Renaming a backup from the restore page (`renameBookmarkBackup`) adds an empty `KEPT_TITLE` folder inside it, which syncs with it and exempts it from pruning and from the limit on every device; clearing the name restores `defaultBackupTitle` (date and tab count) and removes that folder. Like `MARKER_TITLE`, `KEPT_TITLE` is never translated or changed. `bookmarks` is an `optional_permissions` entry requested from the settings page, so updates never prompt existing users; `permissions.request` must be called synchronously inside the user's change handler. If access was revoked, Back up falls back to a file.
- **settings.js** (`options_ui` page): destination (file, bookmarks or both), bookmark retention, backup format and file name pattern, auto-saved to `browser.storage.sync` (synced across the user's Firefox devices). Defaults and accessors live in `settings-store.js`; formats and the `{YYYY} {MM} {DD} {HH} {mm} {ss} {count}` file name tokens live in `formats.js`.
- The JSON shape (`[{title, url}]`) is the contract between export and import — keep them compatible. Other formats only need to keep their links extractable by `parseBackup` in `backup-parse.js`.
- Code uses the Firefox `browser.*` promise-based WebExtension API (not `chrome.*`). The Chrome-oriented `modern-web-guidance:chrome-extensions` skill is general guidance only.
- **Chromium build** (`--env target=chrome`, output `dist-chrome/`): the code runs unchanged since Chrome 148+ provides the same `browser.*` namespace (`minimum_chrome_version` 148); webpack rewrites the manifest (`toChromeManifest`: service worker background, no `browser_specific_settings`/`theme_icons`, adds `icons`) and keeps each message's Chromium wording (see Translations). Code branches on `process.env.BROWSER` (`"firefox"` or `"chrome"`, set by DefinePlugin) only where the APIs differ: the Other Bookmarks folder ID (`unfiled_____` vs Chromium's `folderType: "other"`, preferring the synced copy), folders detected by `node.type` (Firefox) or a missing `url` (Chromium), and `openInReaderMode` (Firefox only). Keep the background script free of DOM APIs; it is a service worker in Chromium.
- **Translations** (`src/_locales/<lang>/messages.json`: en (`default_locale`), de, fr, it, ja, nl, ru, tr, chosen from the add-on's user languages): every user-facing string is a message. Pages mark elements with `data-i18n="key"` (text) or `data-i18n-title` / `data-i18n-aria-label`, filled by `localizePage()` from `src/i18n.js`; the HTML keeps the English text as a fallback. Scripts use `t(key, ...substitutions)` and `plural(key, count, ...)`, which picks `key_one` / `key_other` / other CLDR forms with `Intl.PluralRules` for the translation's own `languageTag` message (count is `$1`). Wording that differs per browser is written `key__firefox` / `key__chrome`; `scripts/locales.mjs` resolves it to plain `key` at build time (e.g. French "marque-pages" in Firefox vs "favoris" in Chrome). `pnpm check-locales` (also run by `pnpm lint`) fails on a `languageTag` that doesn't match its folder, missing, extra or empty messages, plural messages without exactly the forms the language uses for counts 0–1000 (a missing form would silently show English), mismatched `$1` substitutions (only a non-`_other` plural form may omit the count), unknown keys used in `src/`, and descriptions over 132 characters. Dates in backup folder names use the translation's `language` (exported by `i18n.js`), not the browser's content locale. Never translate `MARKER_TITLE` or the default folder name "Tab Backup".
- Styling: `src/main.css` imports Tailwind v4 with a custom `--height-128` theme token and a v3-compat border-color base layer. Prettier uses `prettier-plugin-tailwindcss` for class ordering.

## Versioning and release

- The extension version and add-on ID (`browser_specific_settings.gecko.id`, public on AMO) live in `src/manifest.json`; `package.json`'s version is unrelated.
- Minimum versions: `gecko.strict_min_version` 140.0 (current ESR; Tailwind v4 needs 128+, `data_collection_permissions` 140+) and `gecko_android.strict_min_version` 142.0 (Android gained `data_collection_permissions` in 142). Don't use web platform features newer than these.
- Docs: `README.md` is for users (features, install links, build from source, which AMO reviewers rely on); developer setup and testing live in `docs/DEVELOPMENT.md`, releases in `docs/RELEASE.md`.
- Store listings: `store/listing.md` + `store/screenshots/` (Firefox Add-ons) and `store/chrome/listing.md` + `store/chrome/` (Chrome Web Store; screenshots rendered from the Chromium build so the wording matches). `PRIVACY.md` is the privacy policy linked from both stores; keep it in step with permissions. The store summary and add-ons manager description come from each language's `extensionDescription` message (`__MSG_extensionDescription__` in the manifest; 132 characters max, checked per language and browser).
- The full release procedure (version bump, tag, source zip for AMO reviewers, `web-ext sign --channel=listed --upload-source-code`, Chrome Web Store upload) is in `docs/RELEASE.md`, covering both stores. `pnpm-lock.yaml` is committed so reviewers can reproduce the build with `pnpm install --frozen-lockfile`.
- `make sign-extension` builds and signs `dist/`, reading the AMO API key/secret from 1Password via `op read`; `.env.example` holds the same `op://` references. In Makefile recipes, shell command substitution must be written `$$(...)`. Never inline real secrets.
